# Agent guide for mustr

mustr is a review-first desktop app built as a soft fork of [Zed](https://github.com/zed-industries/zed). It is a client of an unmodified [T3 Code](https://github.com/pingdotgg/t3code) server, which owns agents, pull request data, and worktrees. mustr owns the UI. The plan is in `mustr-docs/PLAN.md`.

## The one rule: don't edit Zed

Pulling in new Zed and T3 Code releases has to stay a routine, scripted task. So:

- mustr's code lives only in mustr's own paths: `mustr-crates/`, `mustr-docs/`, `assets/themes/mustr/`, `script/mustr-*`, `.github/workflows/mustr-*.yml`, and `THIRD_PARTY_NOTICES.md`.
- Never edit Zed's files (`crates/`, Zed's `script/`, `docs/`, `assets/`, and so on). The only touch points are the `mustr-crates/*` line in the root `Cargo.toml`, `Cargo.lock` (regenerated by cargo), `README.md`, `CLAUDE.md`, and `AGENTS.md`.
- If something seems to need a change inside a Zed crate, stop and ask. First look for a public API, a setting, or a pattern to copy into a mustr crate. `crates/zed` has no library target, so copying its helpers is expected; cite the source file in a short comment.
- Syncing with upstream: follow `mustr-docs/SYNC.md` and use `script/mustr-sync-zed` and `script/mustr-sync-t3`.

## Rust and GPUI

Follow these sections of Zed's `.rules`: "Rust coding guidelines", "Timers in tests", and "GPUI". They apply to mustr's crates unchanged.

Ignore the rest of `.rules`, which is for Zed's own repository: the README banner rule, "Pull request hygiene" (Zed's release-notes format), "Crash Investigation" (Zed's Sentry), and "Rules Hygiene".

## Building and testing

- Per crate: `cargo test -p <crate>`, `cargo clippy -p <crate> --all-targets`, and `cargo fmt -p <crate>`. Fix every warning.
- Linux builds need Zed's system packages (`script/linux`). GPUI tests use the test platform and don't need them.
- First builds of Zed crates take minutes; run them in the background.

## T3 Code servers

- `mustr-crates/t3_client` talks to T3 over HTTP and WebSocket. `mustr-crates/t3_client/T3_VERSION` pins the T3 version and orchestration protocol, which must match the server exactly.
- `mustr-crates/t3_api` holds T3's wire types, generated from T3's contracts by `mustr-crates/t3_api/codegen/regen.sh` (see its README). Never hand-edit `src/generated/` or `schema/`. Call RPCs and endpoints through the typed tables: `connection.call::<t3_api::rpc::X>(…)`, `connection.stream::<…>`, and `t3_client::call_endpoint::<t3_api::http::Y>(…)`.
- Live tests are ignored by default. When you run one against a real T3 server, mint a pairing token with only `--scope orchestration:read`, and revoke the session afterwards (`t3 auth session list`, `t3 auth session revoke`).
- Never request `access:write` or `relay:*` scopes, and never print tokens.
- The app pairs on its own when a local `t3` CLI exists, asking for `orchestration:read` and `source-control:write` (`SCOPES` in `mustr-crates/mustr/src/t3_connection.rs`), and keeps its token in the OS keychain. For test runs, set `MUSTR_CREDENTIALS_FILE=<tmp>/credentials.json` so test tokens go to that file instead of the user's keychain, and pass `--user-data-dir <tmp>/data`. `--t3-server <url>` picks the server (default `http://127.0.0.1:3773`), and the hidden `--open-first-pr` opens the first open pull request once the list loads. Set `MUSTR_DRY_RUN_WRITES=1` so the review can't write to the real pull request (comments, reviews, resolving, viewed marks fail locally; reads still work). Revoke the `mustr` sessions afterwards.
- Never open a window on the user's display. Run the app under Xvfb with `VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.json`. Start `xfwm4 --compositor=on` on that display too: without a compositor, GPUI falls back to server-side decorations and mustr's title bar draws no window controls. `ffmpeg -f x11grab` captures the screen.

## Commits and pull requests

- Imperative, capitalized titles without trailing punctuation. Prefix with the crate name when one crate is the clear scope (`review: Add comment cards`).
- Keep each change focused, and say in the description how it was tested.
